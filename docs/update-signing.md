# Update signing

Every Cadence release attaches a `SHA256SUMS.txt` checksum file and a minisign
signature over it, `SHA256SUMS.txt.minisig`. Together they let anyone confirm
two things: that the downloaded artefacts are byte-for-byte the ones the
release workflow produced (the checksums), and that the checksum file itself
came from this project's signing key and not from a substitution (the
signature).

This page documents the mechanism, the current public key, and the rotation
procedure (guide §7.2).

## What is signed

- `SHA256SUMS.txt` — one SHA-256 line per release asset, generated by the
  release workflow from the attached installers.
- `SHA256SUMS.txt.minisign` — a minisign (Ed25519) signature over that file,
  created in the release job **before the release is published**; a missing
  or unusable signing key fails the release rather than publishing unsigned.
- The SBOM and the release notes are not signed; the checksum file covers the
  installers, which are the artefacts the app installs from.

## Verifying a release (manual, works today)

1. Download the release assets plus `SHA256SUMS.txt` and
   `SHA256SUMS.txt.minisig`.
2. Check the artefact hashes:

   ```sh
   sha256sum --check --ignore-missing SHA256SUMS.txt
   ```

3. Check that the checksum file is signed by the project key: save the
   current public key (below) as `cadence-release.pub`, then

   ```sh
   minisign -Vm SHA256SUMS.txt -p cadence-release.pub
   ```

## Where the private key lives

Only as GitHub Actions repository secrets, never anywhere else:

- `RELEASE_SIGNING_KEY` — the minisign secret key file, read by the release
  workflow when it signs the checksums.
- `RELEASE_SIGNING_PASSWORD` — optional passphrase protecting that key. When
  it is not set, the key is stored unencrypted (it is still a secret).

The keypair is generated **on the GitHub Actions runner** by the
hand-triggered [`Signing key rotation`
workflow](../.github/workflows/signing-key.yml) and is written straight into
the secret store with `gh secret set`. It is never generated on, copied to,
or printed from a developer machine, and it never appears in logs, artefacts,
or the repository. The rotation job removes all key material from the runner
when it finishes.

**Bootstrap deviation (recorded, D38).** The key above was generated during
the one-time setup before the rotation workflow could self-store (that path
needs a `SECRET_MANAGEMENT_TOKEN`, which had not been created). Per the
owner's direction the pair was generated locally in a single pipeline that
uploaded the secret key to the repository secret store and shredded the local
material in the same breath — the key's only resting place is the Actions
secret, and no copy remains on any machine. From the next rotation onward the
runner-side workflow is the standing procedure: create the
`SECRET_MANAGEMENT_TOKEN` (One-time setup below) and future rotations never
touch a developer machine.

## One-time setup

1. Create a token the rotation workflow can use to write secrets: a
   fine-grained PAT with **Secrets: read and write** on this repository, or a
   classic PAT with the `repo` scope. The workflow's own `GITHUB_TOKEN`
   cannot manage repository secrets, so this PAT is required. Store it:

   ```sh
   gh secret set SECRET_MANAGEMENT_TOKEN
   ```

2. Optional — if the key should be passphrase-protected, set the passphrase
   **before** rotating:

   ```sh
   gh secret set RELEASE_SIGNING_PASSWORD
   ```

3. Run the `Signing key rotation` workflow (Actions tab → run it by hand).
4. Fill in the *Current signing public key* placeholder above from the job
   summary.

## Rotation procedure

1. (Optional) Update `RELEASE_SIGNING_PASSWORD` first if the passphrase
   should change too.
2. Run the `Signing key rotation` workflow. It generates the fresh pair on
   the runner, self-tests it, stores the secret key as a secret, and prints
   only the public key, key ID and fingerprint to its summary.
3. **Before any further release artefacts are signed with the old key**, ship
   a new Cadence release that carries the new public key, with a Security
   banner in the release notes (and in the in-app release-notes popup). This
   is the guide §7.2 ordering requirement — the app-side updater pins the
   public key as a compile-time constant, so a new app release is the only
   way installed apps learn the new key.
4. Update this page: replace the current key and fingerprint, and record the
   old fingerprint, the rotation date, and the reason.
5. If the old key is suspected compromised, treat it as a security release:
   fix, release, banner, and publish an advisory per guide §6.5 — never
   silently re-sign with the new key.

## App-side verification (planned)

A later slice (recorded in `DECISIONS.md`, D33) teaches the in-app updater to
verify the downloaded installer against `SHA256SUMS.txt` and the minisign
signature, with the public key pinned as a compile-time constant. Until that
ships, the signature serves manual verification, and an update is never
offered as auto-installable on a Failed or Missing-signature state.
